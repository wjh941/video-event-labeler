# CSV 外部修改冲突检测设计

## 目标

防止标注页面打开后，CSV 被 Excel、另一实例或外部脚本修改，随后当前页面保存时把外部修改覆盖掉。

## 方案

- 使用 CSV 原始字节的 SHA-256 十六进制摘要作为 `csv_revision`。
- `AppState` 在加载快照时缓存摘要；需要确认版本时重新计算摘要，并在摘要变化时重新读取、校验 CSV。
- `/api/status` 返回当前 `csv_revision`。
- 浏览器在 `load()` 中保存该版本；`buildPayload()` 将版本放入每次更新请求。
- `/api/update` 在持有 `state.lock` 时先比较客户端版本和当前摘要。版本不一致抛出冲突，不执行任何行修改或 CSV 写入。
- 冲突响应使用 HTTP `409` 和稳定错误信息；成功写入响应返回新版本，浏览器更新本地版本。
- 缺少 `csv_revision` 的旧客户端保留现有兼容行为；新页面始终携带版本。

## 数据流

1. 页面请求 `/api/status`，保存 `status.csv_revision`。
2. 页面请求 `/api/videos` 并允许用户编辑。
3. 保存时发送 `csv_revision`。
4. 服务端锁内计算摘要；相同则按现有校验和原子写入流程保存，不同则返回 `409`。
5. 前端识别 `409`，提示当前保存未覆盖外部修改，保留 dirty 状态；用户刷新后重新加载最新 CSV。

## 错误处理

- CSV 不存在、无法读取或重新解析失败沿用现有 `400/500` 错误处理。
- SHA-256 计算失败不写入并返回服务器错误。
- 冲突不会创建备份、不会写入 CSV；服务端可以先刷新内存快照到外部最新内容，但不会清除前端未保存状态。
- 原子替换和现有文件锁保持不变；摘要检测是覆盖保护，不声称能阻止外部进程在最后检查后直接写文件。

## 测试策略

- 单元测试确认状态暴露非空 `csv_revision`，外部修改后旧版本更新返回 `409`，且外部修改内容仍保留。
- 测试成功更新返回新版本，后续使用新版本可以再次保存。
- HTML 合约测试确认版本被读取、放入 payload、成功后更新，以及 `409` 提示路径存在。
- 保留现有 CSV、HTTP Range、键盘快捷键、断点恢复和完整 HTML 规范化测试。
